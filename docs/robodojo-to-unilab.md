# 我们怎样理解 RoboDojo，再把任务接到 UniLab

我把 RoboDojo 看作一套完整的考试系统。任务是试卷，机器人和物体构成考场，策略是考生，评分代码是裁判。它主要回答同一套条件下不同策略做得怎样。我们借鉴它的任务与评价方式，进一步保留物理后端配置、动作与状态记录，用于后续物理测评

本文对应本地固定源码：RoboDojo f57e1633ffed59761bc8e568cfe7530c4b33381c，UniLab 794c0bbd67771ac48407e084c0164c0e841bfd97。不是团队尚未指定的内部版本

## 一道题从哪里来

以插管为例，task/RoboDojo/config/insert_tubes.yml 指定三根试管和一个管架，以及可选型号、摆放范围等。task/RoboDojo/tasks/insert_tubes.py 定义任务要求、步数限制与评分。Assets/Eval_Layout 里的 JSON 则保存某次评测真正采用的型号、位置、姿态和物理参数

所以配置范围像“出题规则”，固定布局像“这次发下来的试卷”。只有随机种子往往还不够；我们应一起保存源码版本、资产、布局和运行参数

机器人、相机和仿真设置另外放在 env_cfg。换任务时可以复用同一机器人，换机器人时也必须核对动作与观测接口。这里选定的 arx_x5 配置是双臂夹爪；迁移到灵巧手是后续改编，不能直接把原夹爪任务叫作已经接通的灵巧手任务

## 运行时各模块各管什么

| 模块 | 通俗解释 | 具体作用 |
|---|---|---|
| TaskEnv / BaseEnv | 考场总调度 | 建场景、重置、调用机器人和仿真步进 |
| SceneManager | 摆考场 | 加载物体、固定布局和场景属性 |
| RobotManager | 让机器人执行 | 机器人模型、控制与关节状态 |
| Camera / Observation | 给考生看题 | 相机采集和观测组织 |
| SeedManager | 决定本轮试卷 | 按布局文件安排批次和评测实例 |
| RewardManager / Func_Parser | 裁判及判题工具 | 位置、方向、阶段、归位等检查 |
| XPolicyLab | 接入考生 | 策略服务器、模型部署与动作接口 |

策略读取观测后返回动作，机器人执行，仿真更新，再进行评分和记录。当前公开版本 README 明确写了 eval-only；策略接入与服务器由 XPolicyLab 管理，所以不能把 RoboDojo 只理解成一个 RL 训练环境

README 描述 42 个仿真任务和 18 个真实任务，能力维度是泛化、记忆、精度、长时序和开放任务。这与我们的抓取、搬运、转动、插入等“动作类型”不是同一个分类轴。我们可以一层按操作类别分组，再用接触和控制难点解释难度

## 插管到底怎样判分

这道题的终态要求包括三根管子各自满足深度、位置与朝向检查，以及机器人回到原位。过程分则随着满足条件的管子数量依次进入 20、40、100 三个阶段，还要求夹爪张开到给定阈值。每次评价最多推进一个阶段；最后的 100 分仍受最终成功条件约束

源码还有容易漏掉的细节：成功检查满足后会从待检查列表移除，所以成功状态具有记忆，直到重置。迁移时如果只拿当前帧重算成功，语义就变了。我们已把这套阶段与记忆逻辑独立出来，在相同布尔判据输入下与原评分类逐步对照

但不能把这些检查解释得比代码更强。深度检查用的是管架包围盒最高处与试管包围盒最低处的高度差，大于 0.045 m；位置检查使用管架包围盒投影范围及高度条件；朝向检查是试管局部 Y 轴与世界竖直方向夹角小于 30 度。它们不是接触力测量，也不能独立证明试管进入了正确的孔、没有穿透

这正是我们保留物理诊断接口的动机：原任务判分保持可追溯，穿透、滑移、接触力和异常则作为额外诊断记录。要强化成功判据，应建立独立的改编协议，不能无声地替换原规则

## 接入 UniLab 是搬什么

我们搬的是任务定义、资产与控制/评价逻辑，不是把 RoboDojo 的整个程序包在 UniLab 外面就算完成

| 从 RoboDojo 搬出的内容 | 在 UniLab 的位置 | 当前进度 |
|---|---|---|
| 型号、位置、姿态、碰撞和惯性 | 场景/实体与资产配置 | 固定布局已保存，完整场景未迁入 |
| 机器人动作顺序和控制模式 | Action manager | 未适配 |
| 图像、关节和物体状态 | Observation manager | 未适配 |
| 重置、布局选择、随机化 | Event / reset owner | 生命周期要求已记录，未接真实场景 |
| 任务成功和过程分 | Task state + Metrics manager | 已实现插管评分逻辑与指标 term，真实 manager 接口已验证 |
| 超时、结束与失败 | Termination manager | 需区分原评价步与物理步，尚未绑定 |
| 接触、轨迹、计时 | Recorder / metrics / diagnostics | 接口边界已保留，跨后端读取未实现 |

UniLab 的 manager 可以理解为“每一类工作都有一个专门负责人”。例如指标管理器只负责按规定收集指标，任务代码负责告诉它这一步分数是多少。不能把评测分直接当训练 reward：UniLab reward 可能涉及 dt 缩放，评测分则应保留原有 0/20/40/100 的含义

插管的 score 与 success 都采用 last 汇总。不能为了成绩好看改成 max 或 mean。我们的第一版是 CPU 接口验证，尚未把评分状态实现成全 GPU 张量逻辑，不能拿它评价高并发性能

## 我准备按什么顺序推进

先做评分语义和真实 UniLab manager 接口验证；随后补齐插管原场景，用原机器人跑通加载、重置和观测。再接动作控制，检查相同初态与输入下的行为，最后替换为目标灵巧手并增加物理后端

现有 Isaac 环境使用 torch 2.7，当前所查 UniLab 声明 torch>=2.9 和 unisim-core==2.7.1。此次用独立 .venv-unilab 做接口验证，不改服务器已有 Isaac 环境，也不提前声称两个软件栈兼容

第一阶段的验收应当是“评分没有改义、接口能正常收集两行环境数据和部分重置”。只有完整场景实际步进并保存视频以后，才把任务标为接入可运行

本轮结果：评分语义对照通过 100 段合成序列、共 3,000 个评价步；工程回归测试 89 项通过，评分代码独立审查未发现重要问题。随后真实 UniLab MetricsManager 验证也通过：两个合成环境分别得到 100 分和 20 分，部分重置互不影响。证据见 evidence/unilab-metrics-contract.json

原 .venv-unilab 的 CPU PyTorch 下载记录保留为历史失败尝试。实际验证改用独立 .venv-unilab-contract 和本地缓存 torch2.11.0+rocm7.2，仅运行 CPU 合成判据；不代表 GPU 兼容性或完整物理运行

场景预检揭示了当前迁移的实际障碍：UniSim 2.7.1 的九个已登记后端都拒绝以 USD 多实体声明直接装配这四个物体，包含 isaacsim 后端。这只限定本次调用的 entity_assets 装配路径，不代表底层 Isaac Sim 不能读取 USD，也不代表这些后端已安装或启动

所以接下来要先确定受支持的场景装配方式，再加载三根试管和管架，并补齐桌面、机器人与控制。资产已有和路径正确，只解决了“材料齐不齐”，还没有解决“用什么方式把材料装成能运行的场景”。转换时尤其要保留管架的孔洞碰撞表示，否则会出现视觉上有孔、物理上却被封住的错误

当前四个资产哈希已核对，三根试管和管架的原始位置与 wxyz 姿态已写成候选实体声明。质量、摩擦等配置尚未应用；collision=True 只是候选请求，必须核对原运行时配置。不能把这些候选声明作为已复现的任务配置。见 evidence/unilab-scene-declaration.json

同一次静态能力查询中，MJCF 多实体配置存在可用声明，因此优先评估转换为 portable MJCF 的路线。这里只是格式能力查询，没有将 USD 文件改后缀，也没有生成转换后的资产。真正转换还要验证尺寸、惯性、碰撞孔洞和接触行为；声明支持不能代替资产加载验收
